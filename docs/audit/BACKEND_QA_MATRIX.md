## Contract additions (for the front-end owner to record in `docs/RSVP_API_CONTRACT.md`)

`docs/RSVP_API_CONTRACT.md` was not edited. The service is still fully compatible with the contract as written; the following are additive.

1. **`error.fields` on `400 validation`** (`PUT /response`, and `PUT /admin/households/:id/response`). Shape: `{ "error": { "code": "validation", "message": string, "fields": [ { "path": string, "message": string } ] } }`. `fields` is present only when at least one path is known. Paths: `contactEmail`, `notes`, `requestId`, `revision`, `responses` (structural, or a pair outside this invitation: no id is echoed), `responses.<guestId>.<eventId>.status`, `responses.<guestId>.<eventId>.meal`, `plusOneNames` (a name for someone who is not one of this household's plus-one slots: no id echoed), `plusOneNames.<guestId>`. Every guest-fixable problem is returned in one response; `error.message` is the single problem's text or `"N answers need attention. Please review them and try again."`. Suggested client mapping in `src/js/rsvp.js`: `responses.<g>.<e>.status` → `state.errors["<g>|<e>"]`, `plusOneNames.<g>` → `state.errors["name:<g>"]`, `responses.<g>.<e>.meal` → `state.errors["meal:<g>"]`, `contactEmail` → `state.errors.contactEmail`; announce `error.message` in the status region instead of only the generic `MESSAGES.validation`. Nothing breaks if the client ignores `fields`.
2. **`rsvp-settings.cutoffAt` must carry an explicit UTC offset or `Z`** (`2026-11-20T23:59:59-06:00`); the editor returns `400 validation` otherwise. Keep `content/site.config.json` → `rsvp.cutoffAt` in the same form.
3. **`GET /admin/status`** → `rsvp` may include `cutoffInvalid: true` when the configured cutoff cannot be parsed (guest editing is then closed). The guest snapshot's `rsvp` object is unchanged: `{ open, cutoffAt }` only.

## What still needs a deployed environment

- **Mail delivery:** only the `stub` and `webhook` adapters exist; no transactional provider is connected. AT-11 with delivery disabled, then enabled, must be run against the real provider. Provider acceptance is not inbox delivery.
- **Cloudflare Access:** the JWT verification path (`Cf-Access-Jwt-Assertion`, certs URL, `iss`/`aud`/`email` claims) has never run against a real Access instance; the tests use the development bypass. Confirm against current Cloudflare documentation, create the application with MFA in the owners' account, and check that `/admin/status` without a login is blocked at the edge.
- **Rate limiting under real load:** the counters are D1 rows keyed by IP hash and credential digest per 15-minute window; they were exercised sequentially in one isolate. Behaviour under concurrent, geographically distributed traffic (D1 write latency, replica lag) and the NFR "p95 ≤ 1.5 s at 50 concurrent sessions" are unmeasured. Consider Cloudflare's edge rate limiting on `POST /session` as a first layer.
- **D1 batch atomicity in production:** the "same transaction" property behind QA-16/QA-18 was verified in miniflare (`transactionSync`); for production D1 it is a publisher claim.
- **Cross-household cache check (ARCH-04)** on the deployed CDN, and the cron trigger actually firing every five minutes.
- **Restore test, encryption-at-rest confirmation and the owner decisions** listed in `backend/README.md` "Open items before guest launch".
